# WebTransport / TLS 排障手册

> 正常用法见 [README.md](./README.md)。本文只讲**出问题怎么办**。

本文所有命令均已在本机实测通过。

## 1. 30 秒自检

按顺序跑，任何一步不符就跳到对应章节。

```powershell
# ① 网关有没有真的启动 WT（报 wt start failed → 跳 3.1；连这行都没有 → 跳 3.7）
Select-String -Path "<网关工程>\server.log" -Pattern "WebTransport certificate hash|wt start failed|wt listening"

# ② 网关接口返回的哈希，是否与 ① 一致（不一致 → 跳 3.4）
#    注意：网关 WS 端口可能是明文（业务工程默认 tls_cert 留空），此时只有 http 能通。
#    https 失败要接着试 http，别误判成「主证书问题」——这是本手册早期最误导人的一处。
try { (Invoke-WebRequest "https://127.0.0.1:8001/wt-cert-hash" -UseBasicParsing).Content }
catch { (Invoke-WebRequest "http://127.0.0.1:8001/wt-cert-hash" -UseBasicParsing).Content }

# ③ msg-web 转发的哈希，是否与 ② 一致（拿不到 → 跳 3.3）
(Invoke-WebRequest "https://localhost:3020/api/config" -UseBasicParsing).Content

# ④ WT 证书本体是否合规（不合规 → 跳 3.4）
$c = [Security.Cryptography.X509Certificates.X509Certificate2]::new("<网关工程>\certs\wt.pem")
"算法="   + $c.PublicKey.Oid.FriendlyName
"有效期=" + [math]::Round(($c.NotAfter - $c.NotBefore).TotalDays,2) + " 天"
"到期="   + $c.NotAfter
"哈希="   + [BitConverter]::ToString([Security.Cryptography.SHA256]::Create().ComputeHash($c.RawData)).Replace("-","").ToLower()
```

**健康状态**：①②③④ 四个哈希完全相同；④ 算法为 `ECC`、有效期 `10` 天左右（必须 < 14）、到期日晚于当前时间。

> ② 若 https 报错而 http 能通、或返回 `{"hash":""}`，说明网关 WS 是**明文**。
> 这本身不是证书故障，但**WT 一定没启用**（哈希为空 → 前端只能走 PKI → 自签 WT 证书必然被拒）→ 跳 3.7。

> 若你不是在命令行用 `-RedirectStandardOutput` 启动网关（比如在 IDE 里直接 run），
> ① 的日志文件不存在，去 IDE 控制台输出找同样那行即可。其余 ②③④ 与启动方式无关。

## 2. 按页面日志定位

msg-web 页面（`https://localhost:3020`）左侧日志是首选入口：

| 页面日志 | 含义 | 处理 |
|---|---|---|
| `已固定服务器证书 sha256:xxx…` + `✓ WebTransport 连接成功` | **正常** | 无需处理 |
| 有 `已固定…` 但随后 `回退到 WebSocket 连接...` | 哈希与实际证书不符，或证书不合规 | **3.4** |
| **没有** `已固定…`，直接回退 WS | 前端没拿到哈希 | **3.3** |
| 连 `尝试 WebTransport` 都没有 | `enable_wt` 未开或浏览器不支持 | **3.2** |
| WS 也连不上 / 页面显示「不安全」 | 主证书问题，或页面与网关协议不一致 | **3.5** / **3.7** |
| `⚠ 协议不匹配：页面 = https，网关 WS = http` | 页面协议与网关协议不一致 | **3.7** |
| `⚠ 未取得 WebTransport 证书哈希` / `cert_hash` 为空 | 网关没启动 WT（最常见：没配 `tls_cert`） | **3.1 → 3.7** |
| `将在 Ns 后自动重连（第 n/10 次）` | 失败后的指数退避（2s→4s→…→30s 封顶），**预期行为** | 按上面的失败原因处理 |

> 出现 `回退到 WebSocket 连接...` 时**功能没坏，只是退化成 WS**（失去 0-RTT 与队头阻塞优化）。
> 但既然配了 WT，就该查到底。

## 3. 修复手册

### 3.1 网关没打印 WT 证书哈希

```powershell
Get-Content "<网关工程>\server_err.log" -Tail 20
```

| 错误 | 原因 | 处理 |
|---|---|---|
| `wt start failed ... TLSConfig required (browser only trusts real certs)` | **网关没配 `tls_cert` / `tls_key`** → WT 与 QUIC 都不会启动（WS 明文照常服务） | **3.7** |
| `webtransport: load certificate ...` | 证书损坏或密钥不匹配 | **3.4** 强制重签 |
| `webtransport: rotate certificate ...` | 目录无写权限 | 确认 `server/certs/` 可写 |
| `listen tcp 127.0.0.1:8022: bind: ...` | **旧进程占端口** | **3.6** |
| 无错误但也没这行 | `enable_wt: false` 或 `wt_pin: false` | 检查 yaml，然后 **3.6** |

### 3.2 WT 根本没被尝试

检查 `<网关工程>/configs/all/server.yaml`：

```yaml
gateway:
  enable_wt: true   # 必须 true
  wt_pin:    true   # 本地必须 true（生产 false）
```

改完**必须重新编译并重启**（见 3.6），只改 yaml 不重启无效。

### 3.3 前端拿不到哈希

msg-web 每次加载 `/api/config` 会向网关拉一次哈希，失败则留空（前端随即退回标准 PKI → WT 必挂）。

常见原因：

- **网关没启动 WT** —— `gateway.tls_cert` 为空时 WT 与 QUIC 都不会启动，`/wt-cert-hash` 恒返回
  `{"hash":""}`。**这是最常见的一种**，先看 3.1 → 3.7
- **网关没起** —— 先确认 8001 在监听
- **addr 配错** —— msg-web 的 `config.yaml` 中 `addr: 127.0.0.1:8001` 必须指向网关
- **主证书不被 msg-web 信任** —— msg-web 用系统信任库校验网关，主证书有问题时拉取会失败

验证（**https 不通再试 http**：明文网关只有 http 能通，别误判成主证书问题）：

```powershell
# 正常 = {"hash":"<64 位 hex>"}；返回 {"hash":""} → WT 没启用，跳 3.7
try { (Invoke-WebRequest "https://127.0.0.1:8001/wt-cert-hash" -UseBasicParsing).Content }
catch { (Invoke-WebRequest "http://127.0.0.1:8001/wt-cert-hash" -UseBasicParsing).Content }
```

> msg-web 侧同样是「先 https 后 http」取哈希（明文网关下也能取到），并在启动时探测网关协议，
> 结果放在 `/api/config` 的 `gateway_scheme`。

### 3.4 哈希不一致 / 证书过期 / 算法不是 ECC → 强制重签

**最常用的一条修复**，绝大多数 WT 问题靠它解决：

```powershell
# 1. 停掉网关（见 3.6）
# 2. 删掉 WT 专用证书，让网关下次启动重新签发
Remove-Item "<网关工程>\certs\wt.pem"
Remove-Item "<网关工程>\certs\wt-key.pem"
# 3. 重启网关（见 3.6），确认出现 WebTransport certificate hash=...
# 4. 重启 msg-web（它会重新拉取哈希）
```

重签后仍不行，检查新证书是否合规：

```powershell
$c = [Security.Cryptography.X509Certificates.X509Certificate2]::new("<网关工程>\certs\wt.pem")
"算法="   + $c.PublicKey.Oid.FriendlyName                        # 必须是 ECC
"有效期=" + [math]::Round(($c.NotAfter - $c.NotBefore).TotalDays,2)  # 必须 < 14
"到期="   + $c.NotAfter                                          # 必须晚于当前时间
```

任一不满足，浏览器必然拒绝，见 4.2。

### 3.5 WS 也连不上 / 页面显示「不安全」

这是**主证书**（`server.pem`）问题，与 WT 无关：

```powershell
cd mkcert
.\mkcert-v1.4.4-windows-amd64.exe -install
.\mkcert-v1.4.4-windows-amd64.exe -cert-file certs\server.pem -key-file certs\server-key.pem localhost 127.0.0.1 ::1

# 同步到两个实际加载点（不同步 = 仍加载旧证书）
Copy-Item certs\server.pem     <网关工程>\certs\        -Force
Copy-Item certs\server-key.pem <网关工程>\certs\        -Force
Copy-Item certs\server.pem     msg-web\certs\ -Force
Copy-Item certs\server-key.pem msg-web\certs\ -Force
```

然后重启网关与 msg-web。

### 3.6 干净重启（改了代码或配置后必做）

旧进程占端口是「改了没生效」最常见的原因，按端口精确清理：

```powershell
foreach ($p in 8001,8002,8003,8021,8022,8031,8032,8041) {
  Get-NetTCPConnection -LocalPort $p -State Listen -ErrorAction SilentlyContinue |
    ForEach-Object { Stop-Process -Id $_.OwningProcess -Force -ErrorAction SilentlyContinue }
}
Get-NetUDPEndpoint -LocalPort 8001,8003 -ErrorAction SilentlyContinue |
  ForEach-Object { Stop-Process -Id $_.OwningProcess -Force -ErrorAction SilentlyContinue }
Start-Sleep -Seconds 2

# 重新编译（引擎有改动时才需要）
cd <网关工程>
go build -o server.exe .

# 启动
Start-Process .\server.exe -RedirectStandardOutput .\server.log -RedirectStandardError .\server_err.log -WindowStyle Hidden
Start-Sleep -Seconds 6
Select-String -Path .\server.log -Pattern "WebTransport certificate hash|wt listening"
```

> 按进程名猜不可靠：曾出现过占用端口的是 `server-probe.exe` 而非 `server.exe`。

### 3.7 页面协议与网关协议不一致（本次踩到的坑）

**现象**：页面日志反复刷

```
✗ WebTransport 连接失败: Opening handshake failed.
回退到 WebSocket 连接...
连接已断开
正在重连...
```

**根因**（两条独立原因，常同时出现）：

| 通道 | 为什么失败 |
|---|---|
| WebTransport | 网关**没配 `tls_cert`** → WT 服务没启动（日志 `wt start failed ... TLSConfig required`）→ `/wt-cert-hash` 返回 `{"hash":""}` → 前端拿不到哈希只能走 PKI → 自签 WT 证书被 Chromium 拒绝 |
| WebSocket | 网关 WS 是**明文**，而页面是 https → 前端据此派生 `wss://` → 打到明文端口，TLS 握手必失败 |

关键点：**`gateway.enable_wt: true` + `wt_pin: true` 在 `tls_cert` 为空时完全不生效**。
WT 的证书哈希必须经**已受信任的**通道下发（见 4.3），所以引擎把 WT 的准备工作整体放在
`tls_cert` 非空的条件下。

> **现状（已改，别再按旧结论排查）**：两个原本冲突的诉求现在不冲突了——
> 业务工程 `server.yaml` 已配 `tls_cert` 且 **`tcp_tls_disabled: false`（TCP 口也走 TLS）**，
> Unity 客户端在 `config.json` 设 `server.tls: true` 匹配，所以「网关开 TLS」是**当前默认形态**，
> 不是需要二选一的路径 A。TCP/WS 的 TLS 下限已放宽到 1.2，只支持 1.2 的原生 `SslStream` 也能连。
> 排查时先确认**客户端 `server.tls` 与服务端 `tcp_tls_disabled` 相反**，再看证书信任链。

**先判断当前是哪种组合**：

```powershell
# 网关 WS 端口是明文还是加密？（打印「非 TLS」即为明文）
foreach ($p in 8001,8002) {
  $t = $null; $s = $null
  try {
    $t = New-Object Net.Sockets.TcpClient("127.0.0.1",$p)
    $s = New-Object Net.Security.SslStream($t.GetStream(),$false,({$true}))
    $s.AuthenticateAsClient("127.0.0.1"); "端口 $p : TLS"
  } catch { "端口 $p : 明文" } finally { if ($s) { $s.Dispose() }; if ($t) { $t.Dispose() } }
}
```

**两条修复路径，按需求选一条**：

| 路径 | 做法 | 得到 | 代价 |
|---|---|---|---|
| **A. 网关开 TLS**（当前默认；要用 WebTransport 只能走这条） | `<网关工程>/configs/all/server.yaml` 配 `gateway.tls_cert` / `tls_key`（mkcert 证书，见 3.5），并确认 `tcp_tls_disabled: false`，重启网关 | 页面 https → `wss://` 与 WebTransport（哈希经 wss 下发）**全部可用**；TCP 口也加密 | 不支持 TLS 的老客户端连不上：Unity 客户端需 `GameConfig.UseTls=true` 与之匹配（本仓已配）；`robot`/`msg-client` 已自动判定 TLS/明文，无需配置 |
| **B. 工具走明文** | `web.exe -http`（或删掉 `msg-web/certs/*.pem`，工具会自动降级并说明原因） | 页面 http → `ws://` 连明文网关，**立即可用** | WebTransport 不可用（无受信任通道下发哈希）；仅用于"网关没配证书"的临时排查 |

> 两条路都**不用改引擎代码**。若想做到「明文 WS + 可用 WT」，需改引擎让 WT 不依赖 `tls_cert`，
> 但那等于在明文 HTTP 上下发证书哈希、中间人可替换 → **属安全降级，不建议**（见 4.3）。

**验证修复**：重启后网关日志应出现 `gateway: WebTransport certificate hash=...`，
且 `/wt-cert-hash` 返回 64 位 hex；msg-web 启动行会打印 `页面=…，网关=…`，两者应一致。

## 4. 根因与原理

### 4.1 现象：不对称

| 路径 | 结果 |
|---|---|
| Go 客户端走 QUIC | ✓ |
| 浏览器走 TCP / HTTPS / wss | ✓ |
| **浏览器走 QUIC / WebTransport** | **✗** |

只有一种组合失败。这直接排除了服务端、网络、业务代码——**问题只可能在浏览器的 QUIC 证书校验上**。

### 4.2 根因（本机 Edge 实测）

| 实验 | 结果 |
|---|---|
| mkcert 证书（RSA / 2 年，系统已信任）直接连 WT | ✗ `QUIC_TLS_CERTIFICATE_UNKNOWN` |
| 用 `--ignore-certificate-errors` 启动 Edge | ✗ 仍 `Opening handshake failed` |
| 换新 RSA / 换 ECDSA / 补完整证书链 | ✗ 全部失败 |
| 换 `localhost` 或 `127.0.0.1` | ✗ 都失败 |
| **ECDSA P-256 + 有效期 10 天 + `serverCertificateHashes`** | **✓ 成功** |

结论：

1. **浏览器对 WT（走 QUIC）的证书校验不接受本地自建根证书。** 普通 HTTPS 走 TCP 信任系统根库即可，WT 不是同一套。
2. **`--ignore-certificate-errors` 对 WT 无效** —— 它连「绕过」的口子都不给。
   因此**往系统信任库装根 CA 对 WT 毫无帮助**，装多少次都一样。
3. 自签名场景下**唯一**通路是 W3C 的 `serverCertificateHashes`（证书固定）：不走 PKI，
   改由服务端把证书哈希经**已受信任**的 wss 通道下发，浏览器比对哈希放行。
4. 证书固定有**硬性约束**（MDN）：
   - 有效期 **< 2 周**
   - 必须 **ECDSA secp256r1(P-256)，明确禁止 RSA**
   - 前端 `allowPooling` 必须为 `false`

**三个条件必须同时满足。** 只换 ECDSA 而不用证书固定 = 仍走 PKI 路径 = 照样失败。

### 4.3 双证书：为什么不能只留一张

- **WS 需要**「被浏览器信任的长期证书」
- **WT 需要**「短有效期 ECDSA 证书」

两者天然冲突，只能拆开：WT 单独一张，其哈希经已受信任的 wss 通道下发。

```
网关自动生成 wt.pem（ECDSA P-256 / 10 天 / 自动轮换）
   ↓ SHA-256
GET /wt-cert-hash  ← 走已受信任的 wss 通道（8001 TCP）
   ↓
msg-web /api/config 转发给前端
   ↓
浏览器 new WebTransport(url, { serverCertificateHashes })
```

安全性由传输哈希的那条 wss 通道保证。

### 4.4 自动轮换规则

网关每次启动检查 `wt.pem`，满足任一条件即重新签发：

- 文件不存在
- 算法不是 ECDSA P-256
- 有效期 ≥ 14 天
- 剩余有效期 < 3 天或已过期

正常情况下**无需人工干预**。想强制重签就删文件重启（见 3.4）。

## 5. 终极大招：判定服务端还是浏览器

改了半天没头绪时，用 Go 探针直连，**绕开浏览器**验证服务端
（放在 `clover-server-engine` 目录下运行 `go run wt_probe.go`）：

```go
package main

import (
	"context"
	"crypto/tls"
	"fmt"
	"net/http"
	"time"

	iwt "github.com/quic-go/webtransport-go"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 8*time.Second)
	defer cancel()
	tr := &iwt.Transport{TLSClientConfig: &tls.Config{}} // 空 RootCAs = 系统信任库（等同浏览器）
	hdr := http.Header{}
	hdr.Set("Origin", "https://localhost:3020")
	_, sess, err := tr.Dial(ctx, "https://127.0.0.1:8001/wt", hdr)
	if err != nil {
		fmt.Printf("FAILED: %v\n", err)
		return
	}
	defer sess.CloseWithError(0, "")
	fmt.Println("OK: 服务端全链路正常")
}
```

| 探针 | 浏览器 | 结论 | 去哪修 |
|---|---|---|---|
| ✓ | ✗ | 服务端是好的，问题在浏览器侧 | 3.3 / 3.4 |
| ✗ | ✗ | 服务端问题 | 3.1 / 3.6 |
| ✓ | ✓ | 都正常 | — |

> **注意**：探针用系统信任库，浏览器对 WT 走另一套更严格策略。
> 所以「探针能连、浏览器不能连」是**正常且预期**的，不代表服务端有问题——
> 这个反直觉的现象正是当初最误导人的地方。

## 附录 A：本文推翻过的错误结论

留档，避免重蹈覆辙。

| 曾以为 | 实际 |
|---|---|

**这类"听起来很有道理的机制解释"比没有结论更耽误事**，因为它会让人停止怀疑方向。
